Help & Reference Guide

Guide for PIs and users — billing, CLI tools, job submission, and more.

Before PIs can create projects and submit jobs, staff must complete these one-time setup steps:

Step 1 — Import Schools & Departments

Go to Admin Tools → Import Departments (/billing/import-departments/). Upload a CSV with columns: name, code, school, school_code, affiliation. The affiliation column accepts the Affiliation's code (orga, orgb) or its display name (OrgA, ORGB), case-insensitively — matching on code alone once silently rejected every OrgB row. school / school_code likewise match an existing School by either field, and re-importing heals affiliation drift on rows that already exist. This creates the School → Department hierarchy used for Slurm account placement and billing.

Step 2 — Create Slurm Cluster

Go to Django Admin → Slurm Clusters. Create a cluster record with:

  • Name — must match Slurm's cluster name: cluster-x in production (bare metal), my_cluster-dev on the dev Docker stack. my_cluster is not a cluster name.
  • Type — container (dev Docker) or bare_metal (production). There is no docker value; the model choices are container / bare_metal, and the field defaults to bare_metal.
  • Root account — top of Slurm hierarchy: my_cluster / root for a shared cluster (Model A/C, both affiliations synced), or orga / orgb for a single-org cluster (Model B, allocations of the other affiliation filtered out)
  • TRES types — default cpu,gres/gpu,billing (GPU budgets enforced); drop gres/gpu only on a CPU-only cluster
  • Manage config — leave unchecked on an externally-managed production cluster such as cluster-x: the per-cluster mirror slurm.conf then becomes the absolute source of truth and ColdFront never regenerates it. The admin form refuses to enable it on a prod host.
Step 3 — Create Partitions & Nodes

Go to Django Admin → Slurm Partitions. Create partition records and assign nodes. The CLOACK standard set is the free scavenger, the CPU billing tiers low, med, high, and the GPU partitions named after the hardware — a100, l40s, h100, h200 (OrgA) and b200, b300 (OrgB). Set AllowQos and TRESBillingWeights as needed. premium is not a partition on cluster-x — do not use it in examples.

On an externally-managed cluster (manage_config=False, e.g. cluster-x) do not hand-create partitions here: the live controller owns the topology and coldfront import_slurm_cluster --cluster <name> --update mirrors partitions and nodes back into ColdFront (the scheduled reverse import runs every 10 min). To hide a partition from the Submit Job page and the resource catalogue, uncheck is_available — never delete the row, the reverse import recreates it.

Step 4 — Configure QOS

Go to Django Admin → Slurm QOS. A dev Docker cluster is seeded automatically with scavenger, interactive and orgb (plus the legacy normal / premium, kept only for backward compatibility). ensure_in_slurm=True is the only trigger for the sync to create a QOS in Slurm or assign it to an account — there is no hardcoded fallback, so a cluster with no flagged rows keeps whatever policy its own slurm.conf/sacctmgr already has. Mark scavenger as is_free=True so it is never billed.

Production (cluster-x) uses the role taxonomy instead (SlurmQOS.role + affiliation): scavenger (free, DefaultQOS), orga (paid OrgA), orgb (paid OrgB), condo and class, with the elevated tiers orga2 / orga4 pinned per account through the QoS / DefaultQoS allocation attributes. normal and premium are retired there — never document --qos=normal or call "normal, premium" the paid QOS.

Step 5 — Set Billing Rates

Go to Django Admin → Billing Rates. Create rate records for each rate type (cpu_full, cpu_om, gpu_full, gpu_om, storage, backup) with effective dates.

Billing is driven by IO Numbers (CostCenter), not by the rate catalogue alone — an allocation with no pay-role IO link is never charged. Staff pause, resume and edit any IO at Billing Management → IO Numbers (/billing/cost-centers/all/); a PI toggles their own at My Usage & Billing → Cost Centers. An allocation whose pay IOs are all paused is recomputed is_billable=False / no_charge by the rule engine, and on the Slurm side the account association (not the individual users) gets GrpSubmitJobs=0 — ColdFront owns that zero and lifts it back to -1 only when the live value is 0. The free default/scavenger account is a sibling leaf under pi-<user> and is never touched. Paused and inactive IOs are refused as new links; existing links are kept. Pausing opens a helpdesk ticket, resuming resolves it.

Step 6 — Activate Terms of Service

Go to Admin Tools → Import ToS (/billing/import-tos/) to upload a ToS CSV, or create directly in Django Admin → Terms of Service. Set is_active=True on the current version. Only one version can be active at a time.

Important — activating a ToS locks the whole portal, not just project creation. TosAcceptanceMiddleware redirects every authenticated user who has not accepted the active version to the acceptance page on every request. Only the usernames admin, root and coldfront and the paths /admin/, /oidc/, /static/, /api/, /user/login, /user/logout and /billing/tos/accept are exempt — superusers are not, so you will be bounced to the acceptance page yourself on your next click. Keep /admin/ in mind as the way back in if a ToS is published by mistake. With no active ToS the gate is inert.
The Slurm gate is universal: anyone who would receive an association — PI, member or staff — is skipped by the sync until they accept, so they can log in but cannot submit jobs. The user_required checkbox on the ToS record is no longer consulted (user_needs_tos ignores it); it survives only as a legacy field, so do not rely on leaving it off to exempt regular users.
Step 7 — Check the ColdFront Resource

The Cluster Resource that PIs select when requesting an allocation is auto-created: a post_save signal on SlurmCluster creates and links one the first time the cluster is saved without a resource, naming it after the cluster (cluster-x → CLUSTER-X). This fires identically from the Admin UI, ./start.sh slurm create and the seed scripts, so there is normally nothing to create by hand. Open Django Admin → Resources only to confirm the row exists and to adjust its description or visibility. OrgA and ORGB are not Resources — they exist only as Affiliation records.

Ready! Once all steps are complete, PIs can create projects, request allocations, and start submitting jobs after staff approval.
  1. PI creates project — sets title, abbreviation, department and IO Number. Must accept ToS if active. Project Storage is not part of this form — the PI requests it afterwards from the Project Storage card on the project page, and staff approves it.
  2. PI requests allocation — chooses the cluster resource, writes a justification and, for a paid allocation, picks the Pay IO Number that will fund it. Core-hour and GPU-hour budgets are not typed in here — they are seeded from the cluster's own defaults when the allocation is activated.
  3. Staff reviews & approves — allocation moves to Active.
  4. Auto-seed on activation:
    • Default attributes seeded: Core Usage (Hours), Extra Core usage (Hours), Accelerator Usage (Hours), Extra Accelerator Usage (Hours), plus the blank QoS / DefaultQoS overrides
    • Billing is not computed here — the billing record is created (and refreshed) only when staff runs Computing Billing on the Billing Report
  5. Slurm account provisioning (real-time) — creates the account hierarchy root → school → department → pi-<user> → account. The free default account and every paid project account are sibling leaves under the structural pi-<user> node, so each one carries its own budget. PI must have accepted ToS for their user association to be created.
  6. ToS acceptance triggers Slurm association — when PI accepts ToS, a post_save signal immediately provisions their user association on all active allocations. Every user is gated the same way — a member is added to the Slurm account only after they, too, have accepted the active ToS.
  7. Periodic sync (safety net) — sync_slurm runs every 15 minutes, catches any missed associations. Respects ToS gating.
  8. LDAP sync — ensures the user exists in LDAP with a home directory, and sets the cluster login shell. The shell is policy-derived on every sync: /bin/bash only for a user sponsored by a PI (member of a PI group / active allocation member) who has accepted the current ToS when one is active; everyone else keeps /bin/false and cannot log in to a login node.
  9. Users submit jobs — job records are imported from Slurm every 15 minutes, with a deeper 7-day re-import nightly at 02:45. Dollar charges are produced separately, when staff runs Computing Billing.
  10. Billing hold (optional) — a PI can pause an IO Number from My Usage & Billing → Cost Centers (staff can pause, resume or edit any IO from Billing Management → IO Numbers). While every Pay IO of an allocation is paused the allocation is not billable and no new jobs can be submitted on that paid account; the free default (scavenger) account is never affected. See Pause billing on an IO Number.

2. GrpTRESMins — Usage Limits

Each allocation account gets a GrpTRESMins limit derived from the Core Usage (Hours) and Accelerator Usage (Hours) allocation attributes. The TRES types are configured per cluster via SlurmCluster.tres_types (default: cpu,gres/gpu,billing).

Scenariocpu=billing=
No weekly cap hours × 60 hours × 60 (same value)
Weekly cap set ($X) hours × 60 (core hours) $X × 1,000 × 60 (cap in billing minutes)

Detection: when billing ≠ cpu in GrpTRESMins, a weekly cap is active.

Reset window: every GrpTRESMins TRES (cpu, gres/gpu, billing) is checked against the same association usage counter, which slurmctld clears on PriorityUsageResetPeriod. On cluster-x that is MONTHLY (since 2026-09-21, matching the one-month billing period), so the field still labelled “Weekly Cap ($)” is enforced per month there, and the per-allocation core / GPU-hour budgets are monthly quotas — the default (scavenger) seed is 180,000 core-h per month (6,000 units × 30 days). ColdFront's Core Hours Reset must be set to Monthly to match. The Sunday 00:00 boundary applies only to a cluster configured WEEKLY. ColdFront never resets Slurm — check_and_run_core_hours_reset only zeroes the ColdFront gauges. 

# Example: 1000 core hours + $50 weekly cap

# No weekly cap: billing = cpu
sacctmgr update account set grptresmins=cpu=60000,billing=60000 where account=jsmith_proj1

Computing Billing (manual)
No scheduled task writes to the billing ledger. Both AllocationBilling rows (the "Billing Rules" grid) and SlurmAccountUsagePeriod rows (the "Usage & Charges" table) are created only when staff clicks the Compute Billing button on /billing/report/.

The button runs two management commands in sequence:

docker exec coldfront coldfront recalculate_billing --all   # billing rules
docker exec coldfront coldfront sync_job_usage              # usage periods

Until the button (or the CLI above) is invoked, the report stays frozen on whatever was last computed. The 15-min sync_slurm_all task keeps updating the Core Usage gauge and per-user snapshots, but never touches billing rows.

Why manual: staff asked for a predictable, explicit compute step so the report never grows new rows on its own. Prevents accidental double-counting mid-month and makes the ledger reproducible.

How It Works

Spend caps are enforced at the Slurm account association level using GrpTRESMins on the billing TRES. This is set directly on the account, not via per-allocation QOS.

The cap is a dollar amount; the period it covers is whatever PriorityUsageResetPeriod the cluster runs, because that setting clears the usage counter the limit is checked against. On cluster-x that is MONTHLY (since 2026-09-21), so the field labelled “Weekly Cap ($)” is in practice a monthly ceiling there: once the month's spend reaches it the account stops until the 1st.

Conversion Formula
1 SU (Service Unit) = $0.001
1 dollar = 1,000 SU
Slurm GrpTRESMins = SU-minutes

Formula: $X × 1,000 × 60 = GrpTRESMins

Example: $30 per reset period (monthly on cluster-x) → 30 × 1,000 × 60 = 1,800,000 SU-minutes

Important — who resets what: Slurm itself clears the usage that GrpTRESMins is checked against, on the PriorityUsageResetPeriod schedule in slurm.conf. On cluster-x that is MONTHLY since 2026-09-21 (the billing period is one month), with PriorityDecayHalfLife=30-0 still decaying inside the month. That counter is one per association, shared by cpu, gres/gpu and billing — so on cluster-x the spend cap and the per-allocation core/GPU-hour budgets are all monthly quotas, and ColdFront's Core Hours Reset must be set to Monthly to match. The Sunday 00:00 machinery in ColdFront (?week_start= on the weekly-usage API, sbalance --week, billing_queries.current_week_window and the Core Hours Reset Weekly period) only lines up with the controller on a cluster actually configured WEEKLY; on cluster-x those views show one week's slice of a month-long counter. check_and_run_core_hours_reset only zeroes the ColdFront gauges and never touches Slurm.
Weekly Cap Usage (live)

Served on demand by GET /api/v1/allocations/<pk>/weekly-usage/: slurmrestd jobs in the current Sunday→Saturday window (?week_start=YYYY-MM-DD for a past week, interpreted as 00:00 cluster-local — pass a Sunday). Current-week hits UPSERT the Weekly Cap Usage ($) attribute with a 5-minute debounce.

On cluster-x the controller resets usage monthly, so this gauge (a Sunday→Saturday slice) is narrower than the period the cap is actually enforced over: spend accrued earlier in the same month still counts against the limit even though it has dropped out of the week shown here.
What is TRES?

Trackable Resources (TRES) are Slurm resources that can be tracked for usage and limited. Common types: cpu, mem, gres/gpu, billing.

Cluster TRES Types

Configured in Admin > Slurm Clusters > "Slurm Account Defaults" via the tres_types field. This defines which TRES types receive GrpTRESMins budget limits. The default is cpu,gres/gpu,billing (GPU budgets enforced out of the box since migration 0117). Values are TRES-minutes: the writer stores hours × 60.

Cluster Typetres_typesGrpTRESMins Example
CPU-onlycpu,billingcpu=10800000,billing=10800000
GPU-enabled (default)cpu,gres/gpu,billingcpu=10800000,gres/gpu=60000,billing=10800000

The numbers above are the current default-project (scavenger) seeds on a monthly cluster: 180,000 core-hours → 10,800,000 core-minutes and 1,000 GPU-hours → 60,000 GPU-minutes. Both seeds are per-cluster admin fields (default_core_hours / default_accel_hours; paid allocations use paid_core_hours / paid_accel_hours, seeded at 100,000,000).

Only cpu, gres/gpu and billing may be listed here. They are the only TRES that share the minutes scale the writer emits. Listing mem hands it the core-minutes value as MB-minutes and freezes every job with AssocGrpMemMinutes (cluster-x, 2026-07-16). tres_types is NOT a mirror of slurm.conf AccountingStorageTRES — tracking and budgets are independent, and tracking-only TRES belong in the conf file, never here.
A GrpTRESMins budget is a quota per usage-reset period, not a lifetime total. Slurm checks it against the association's accumulated usage, and that ONE counter — shared by cpu, gres/gpu and billing alike — is cleared by PriorityUsageResetPeriod. cluster-x runs MONTHLY (since 2026-09-21, matching the one-month billing period), so on production every core-hour and GPU-hour budget is a monthly quota and a "Weekly Cap ($)" value is likewise enforced per month. Keep ColdFront's Core Hours Reset on Monthly to match: it only zeroes the ColdFront gauges and SlurmUserUsageSnapshot, it never resets Slurm's counter. Enforcement also requires priority/multifactor; the dev template sets no PriorityType, so budget limits do not decay or reset there — verify before trusting them in dev.
TRESBillingWeights (per partition)

Configured on each SlurmPartition in Django Admin. Generates the TRESBillingWeights="..." directive in slurm.conf. 

# Weights are milli-dollar: weight = ($ per unit-hour) x 1000   (1 SU = $0.001)
# Example — a100 at $0.555 per GPU-hour:
TRESBillingWeights="CPU=55.5,Mem=5.328G,GRES/gpu=555"

# CPU tier seeds: low CPU=5.6,Mem=1.4G | med CPU=6.2,Mem=1.55G | high CPU=10.7,Mem=2.675G
# Default (when blank): 1 CPU-minute = 1 billing unit, all other TRES = 0

This determines how Slurm converts mixed resources into a single "billing" number. The billing TRES is what GrpTRESMins=billing=X limits against.

PriorityFlags=MAX_TRES — it is the MAX, not the sum. cluster-x sets it (and so does the dev template), so a job's billing rate is max(cpus × W_cpu, mem_gib × W_mem, gpus × W_gpu) — the single most expensive resource the job holds, never the total of all three. Every estimate surface mirrors that same formula (Submit Job modal, the [BILLING] breakdown in cli_filter.lua, the job_submit.lua cost gate), so an estimate matches what sacct later records. A partition with a blank tres_billing_weights falls back to the BillingRate catalog instead ($ per SU, 1 SU = one hour of the resource).

Run stree -r root on a login node to see the live hierarchy (slurmtree is an alias of the same tool; -r root and --full are admin-only — without -r the tree is auto-detected from $USER). Add -M cluster-x to target the production cluster explicitly: -M is a documented flag on CLOACK's own wrappers (stree, sqos, sfeatures, sbrief), never on sacct/sreport/squeue/sacctmgr. Two attributes on every allocation — QoS (the allowed QOS list) and DefaultQoS (the single default) — let you pin exactly which Slurm QOS an account may use: to keep a group off partitions they shouldn't reach, to grant an elevated GPU tier (orga2 / orga4), to attach a course account to class, or to bind a condo account to its condo_* QOS. They live in the Allocation Attributes table on the Allocation Detail page and are edited inline by staff as a select of that cluster's QOS names (blank = “— cluster default —”); PIs see them read-only.

Why this exists: ColdFront is the source of truth and the sync_slurm task re-asserts each account's QOS every 15 minutes, so a manual sacctmgr modify ... set defaultqos= is reverted on the next pass. Filling these attributes makes the sync enforce your restriction instead of reverting it.

Project Storage is the Weka filesystem as a single thing — one filesystem per PI, one directory per project. Its value is the total capacity and it includes the Cache (the flash/SSD share). The split is invisible in the filesystem; PIs never see the words "object", "tier", "hot" or "cold". Scratch storage (per-PI /scratch) is a separate thing and is not part of Project Storage.

How PIs request it: the Create/Update Project forms no longer carry storage fields. PIs use the Project Storage card on the Project Detail page (Request Storage Change) to submit a change request (Project Storage TB + Cache TB + justification, which is required above the Cache cap). The request is pending until staff approves or denies it — values only land on the project at approval, and a "Project Storage under review" banner plus a Pending review badge sit on the project page meanwhile. One pending request per project: cancel it to submit different values. The card is not offered on default or archived projects, and condo (hardware-credit) projects are staff-managed — their PIs ask the Arch team instead of submitting.

Rules (validated at submit AND re-checked at approval): Cache ≤ Project Storage; the PI's total Cache across all projects must fit the PI's effective Cache cap (10 TB by default, or a per-PI cap set by staff). Requests above the cap require a justification and an explicit staff override at approval. The re-check uses live sums, so another of the PI's projects growing in the meantime can make a pending request fail review.

Billing: the Cache and the Project Storage total are each billed per TB-month from the rate catalog. The charge does not depend on jobs — a billable allocation with provisioned storage gets a monthly usage period, so the invoice carries the Cache (TB) and Project Storage (TB) lines even in a month with zero compute.

Field mapping (legacy names kept): storage_tb = Cache → Weka ssd_capacity; backup_tb = Project Storage total → Weka total_capacity. Billing: rate type storage bills the Cache, backup bills the Project Storage total.

One WekaFS filesystem per PI. ColdFront sums the PI's projects and provisions the filesystem with replace semantics: the FS tracks the summed provisioned values exactly (grows and shrinks; Weka itself refuses any shrink below used data, which surfaces as a sync error).

Names and layout (flat, user decision 2026-09-04 — matches mgmt-host manual practice): the filesystem is named after the PI's LDAP uid (admin1, orgb-aviralku) and provisioning mkdirs the flat ${PROJECTS_MOUNT}/<pi>/ (default /projects) — no orga/orgb tree and no per-<abbrev> subdirectory. The dir is chowned <pi>:<pi-group> 770 only when newly created; an existing dir is never re-chowned, because ops sets custom ownership deliberately. Members of a PI whose paid project carries provisioned storage get a projects_<pi> symlink in their home, reconciled convergently by every sync_ldap pass — an approval (and staff Edit Provisioned) dispatches a per-PI sync so the links appear on approval day.

Weka rule: ssd_capacity ≤ total_capacity — the Cache is a slice of the total, not an addition to it. That is why the portal enforces Cache ≤ Project Storage at PI-level sums, plus the Cache cap (WEKAFS_PI_HOT_CAP_TB, default 10 TB, per-PI override on the user profile). A PI with Cache but no Project Storage total gets an all-SSD filesystem sized to the Cache sum (legacy shape).

Units and guards: capacities are sent in decimal TB (tb_to_bytes), so a 3 TB request reads as exactly 3.00 TB in the Weka GUI; the at-target check tolerates 4 KiB block rounding. A Cache sum larger than the Project Storage sum is clamped down to the total with a WARNING (Weka requires ssd_capacity ≤ total_capacity). An untiered filesystem rejects an explicit ssd_capacity (UntieredFilesystemCannotSetSSDCapacity), so the payload omits it whenever no object store is attached. Reads tolerate the live API shape: GET /fileSystems reports total_budget / ssd_budget (not total_capacity), and rows with is_removing=true are skipped — a PUT against one 400s.

Naming history (staff awareness): until 2026-08-21 the portal said "Hot Storage" (= today's Cache) and "Cold Storage" (= today's Project Storage total). Field names storage_tb/backup_tb and the Weka payload are unchanged — labels only. The object store applies at filesystem creation only (WEKAFS_OBS_NAME, or the per-affiliation fallback WEKAFS_OBS_NAME_OrgA / WEKAFS_OBS_NAME_ORGB when the shared name is blank); attaching one to an existing filesystem is a manual weka fs tier obs attach (or delete + re-sync).

Debugging: set WEKAFS_DEBUG=true in wekafs.env and run ./start.sh wekafs-sync; every API call and provisioning decision is appended as JSON lines under ${BASE_DATA}/coldfront/log/wekafs/ (container path /opt/coldfront/log/wekafs). Gotcha: wekafs-sync is append-only to .env — changing a key that is already there needs a manual edit of .env plus a forced recreate of coldfront/qcluster, or the container keeps the old value. Project Storage changes flow through a request → approve lifecycle (model StorageRequest): the PI submits from the Project Detail "Project Storage" card; staff reviews at Storage Review (sidebar → Admin/Staff Tools). Reviewers: superusers or staff with Elevate to superuser for approvals. At most one pending request per project — the PI cancels it to submit different values. Submit-side gates: default and archived projects cannot request storage at all, and on a condo (hardware-credit) project only staff may submit (the PI is told to contact the Arch team). While a request is pending, Project Detail shows a "Project Storage under review" banner and a Pending review badge on the card.

The queue lists pending requests oldest-first with the PI's Cache after approve (their other projects plus this request) against the effective cap, flagged when over. That figure is simulated per row in isolation, so two pending requests from the SAME PI interact only at approval time, where the live re-validation decides. The last 20 reviewed requests are listed underneath.

Approve (in order): re-validates the cap with live sums → applies the values to the Project (storage_tb/backup_tb + enable flags) → recalculates AllocationBilling for the project's allocations → best-effort WekaFS provisioning. While the cluster kill-switch wekafs_sync_enabled is OFF (or WEKAFS_API_ENDPOINT unset) the provisioning step is a silent no-op — staff provisions manually via the CLUSTER-X ticket that opened at submit. Once sync is enabled, the same approval provisions automatically. The same on-commit hook dispatches a per-PI LDAP sync so the projects_<pi> member symlinks appear on approval day instead of at the next scheduled pass. The submit-time ticket is linked to the StorageRequest (Admin → Helpdesk ticket links), so approve and deny post the resolving follow-up and a PI cancel closes it.

Over-cap requests: a request above the PI's effective Cache cap can only be submitted with a justification, and only approved via "Approve (override cap)" — the override is stored on the request (cap_override) and in the audit trail. Standing exceptions: set the per-PI Cache cap (TB) on the Staff User Profile page or in the UserProfile admin.

Edit Provisioned (reviewers only — button on the Project Storage card, project/<pk>/storage/provisioned/) sets the PROVISIONED values directly with no request round-trip: for legacy values left by the pre-review project form, or to reconcile the ledger with what really exists on Weka. Same validation, billing recalculation and best-effort WekaFS provisioning as an approval; over-cap values need the Override cap checkbox. A pending request is left untouched — approve or deny it separately. To move a whole host's pre-0135 form-era values into the queue instead, run coldfront legacy_storage_to_review inside the coldfront container (dry-run by default; --yes applies, --project N scopes one project): it opens a pending request per project and zeroes the provisioned fields, so approval re-applies them through the audited path.

Source of Truth

The Slurm account hierarchy (root → school → dept → pi-<user> → {default, projects}) is driven by Project.department — the single source of truth since 1f42961d (2026-08-06). The invariant is "never NULL": on_project_saved_ensure_department materializes the affiliation fallback (CLOACK for OrgA, orgb-dep for OrgB) onto every project. The AllocationBilling.department passes survive only as a legacy secondary net and are inert once the invariant holds.

Priority Order

One project per PI wins the pi-<user> tree node, ranked as:

  1. Rank 0 — any non-default project (its department was chosen deliberately by the PI or staff, even when that department is CLOACK), and a default project whose department is not the affiliation placeholder (staff edited it)
  2. Rank 1 — a default project still carrying the affiliation placeholder (FALLBACK_DEPT_CODES = CLOACK, orgb-dep) that _create_default_pi_project materialized at promotion — nobody chose it
  3. Ties break on the lowest project id, so a PI whose default project already holds a real department behaves exactly as before the ranking
  4. Legacy secondary nets, inert once the invariant holds: non-default AllocationBilling.department, then default AllocationBilling.department
  5. Defensive final fallback: CLOACK for OrgA, orgb-dep for orgb-*. The old NODEP and SS codes no longer exist (removed by 1f42961d).
Auto-Propagation Signals
  • Setting AllocationBilling.department on a default project → propagates to Project.department
  • Setting AllocationBilling.department → adds department to PI's UserProfile.departments
  • Adding a PI to a department → sets that department on their projects that have none. Inert in steady state: the signal filters on Project.department__isnull=True, and on_project_saved_ensure_department materializes the affiliation fallback (CLOACK / orgb-dep) on every save, so no project is ever NULL. To move a PI in the Slurm tree, edit the department of the project that wins the ranking above — adding the PI to a department will not reparent anything.

What period does the cap cover? The cap is checked against the Slurm association usage counter, which is cleared on the cluster's PriorityUsageResetPeriod. On cluster-x (production) that has been MONTHLY since 2026-09-21, so a “Weekly Cap ($)” amount is what you may spend per month there, and your allocation's core-hour / GPU-hour budgets are monthly quotas as well (a free default allocation seeds 180,000 core-hours per month). The Sunday 00:00 boundary applies only to a cluster configured WEEKLY. ColdFront never resets Slurm usage — the scheduler owns that counter.

Jobs refused with a billing hold. If every pay IO Number funding your allocation is paused, the account is put on hold (GrpSubmitJobs=0) and Slurm refuses new submissions; jobs already queued or running are not killed. A PI resumes the IO Number at My Cost Centers (IO Numbers) (My Usage & Billing → Cost Centers) and submission is restored on the next sync. Your free default (scavenger) account is a separate Slurm account and keeps accepting jobs throughout.

The Terms of Service (ToS) system requires every user who will receive a Slurm association — PI, member or staff — to accept the active usage policy before they can run jobs; PIs are additionally blocked from creating projects or requesting allocations until they accept. Who must accept (universal gate)

The legacy User Required checkbox on the ToS record is no longer consulted: user_needs_tos() in tos_utils.py ignores it, and the sync applies the gate per user at provisioning time.

  • A user who has not accepted is skipped when the sync adds members to a Slurm account, so they cannot submit jobs.
  • The acceptance card appears on the User Profile page for everyone, and on Project Detail (PI and member forms), the Project Creation form and the Allocation Request form.

Real-time Account Provisioning

When staff approves an allocation (status → Active), the system immediately creates the full Slurm account hierarchy: root → school → department → pi-<user> → project account. The bare default account and every project account are sibling leaves under the structural pi-<user> node, so each carries its own GrpTRESMins budget. Parented account creates go through sacctmgr (CLI-by-design — slurmrestd v0.0.42 corrupts parent_acct/lineage); user associations still go over REST.

User associations are gated by ToS acceptance: the PI's user association is only created if they have accepted the current ToS. Every other member is gated identically — the association is created only once that user has accepted the active ToS. The legacy user_required flag is no longer consulted. When a user later accepts ToS, a post_save signal on TOSAcceptance triggers immediate provisioning of their Slurm association.

This is best-effort: if the REST API is unavailable, a warning is logged and the periodic sync_slurm (every 15 minutes) acts as safety net. The provisioning respects Model B affiliation filtering — an OrgA PI allocation approved on a OrgB-only cluster is silently skipped.

PI billing hold (IO pause)

The same 15-minute sync converges CostCenter.billing_paused. When every Pay IO of an allocation is paused, the rule engine recomputes it is_billable=False / no_charge and the sync writes GrpSubmitJobs=0 on the account association (one write covers every current and future user assoc). ColdFront owns that zero: it lifts it back to -1 only when the live value is 0, so an ops-set positive GrpSubmitJobs is left alone — freeze a non-paused account with MaxJobs/GrpJobs=0 instead. The free default/scavenger account is a sibling leaf under pi-<user> and is never touched. Write path is CLI-by-design (sacctmgr modify account … set GrpSubmitJobs=…): the REST assoc upsert has already cleared GrpTRESMins on 25.11.

All ColdFront → Slurm sync paths (coldfront2slurm, collect_slurm_acc_info, collect_sacct, real-time account provisioning) use the slurmrestd REST API as the primary channel. Since Phase 4 the sacctmgr CLI is a conditional fallback, not an automatic one: on a bare-metal cluster such as cluster-x (with REQUIRE_SLURM_CLI=False) a REST failure logs an ERROR and skips the mutation instead of degrading to the CLI.

Why the fallback exists — and when it is allowed
  • Allowed only when the cluster is Docker (cluster_type=container — Slurm 22.05 in containers has broken JWT auth), settings.REQUIRE_SLURM_CLI=True, or the run is --dry-run. Outside those three cases there is no fallback at all.
  • Resilience during slurmrestd restarts, JWT rotation, or Slurm upgrades that change the REST API version.
  • Dev environments where slurmrestd is not configured still work via sacctmgr.
  • Where the CLI is allowed, failure is transparent: the sync run completes; the next run retries REST. Where it is not allowed (bare-metal, REQUIRE_SLURM_CLI=False) the mutation is skipped, an ERROR is logged, and the next run retries REST.
CLI-by-design operations (never a REST regression)

Some mutations run sacctmgr first and fall back to REST, because slurmrestd v0.0.42 cannot perform them correctly. They bypass the gate above and are recorded under an <op>_cli_by_design operation name:

  • Parented account creates / reparents — REST writes id_parent but never parent_acct, so the account is born with corrupted lineage and is invisible to sreport.
  • All account and user-association deletes — the REST DELETE attaches an update_time condition and slurmdbd answers rc=1900 "Data has not changed since time specified" without removing anything.
  • QOS MaxTRESPerAccount / MaxTRESPerUser and condo GrpTRES drift convergence.
  • IO-pause GrpSubmitJobs — when every pay IO Number funding an allocation is paused (CostCenter.billing_paused), the sync writes GrpSubmitJobs=0 on the account association, not per user: account-level Grp* is hierarchical, so one write covers every current and future user assoc. ColdFront owns that zero and lifts it back to -1 only when the live value is 0 (an ops-set positive value is left alone). The free default/scavenger account is a sibling leaf under pi-<user> and is never touched. Ops rule: freeze a non-paused account with MaxJobs/GrpJobs=0, never GrpSubmitJobs=0 — that zero is lifted on the next pass. PIs toggle it at My Usage & Billing → Cost Centers; staff pause/resume/edit any IO at Billing Management → IO Numbers (/billing/cost-centers/all/).
What to expect in logs

Two INFO lines mark the case where the REST client could not be built at all (SlurmClient.ping() failed). They are emitted once per sync run — not per call — and everything after them in that run uses sacctmgr:

coldfront2slurm: REST API unavailable (Connection refused), using sacctmgr CLI
collect_slurm_acc_info: REST failed (...), falling back to CLI

A per-operation REST failure logs nothing at all where the fallback is allowed — it only writes the cli metric row described below. Where the fallback is not allowed (bare metal such as cluster-x with REQUIRE_SLURM_CLI=False) it logs at ERROR and the mutation never happens:

coldfront2slurm: REST <op> failed and CLI fallback disabled (cluster=cluster-x): ...

Read the INFO pair as “this whole run degraded to the CLI” and the ERROR line as “this mutation was skipped”. Investigate either if it recurs in production.

Forcing a specific path (debugging only)

Both dev and prod Slurm clusters run Slurm 25.11.2 with JWT authentication enabled on slurmrestd. This is what allows ColdFront → Slurm REST calls (the fast path in Slurm Sync: REST API + CLI Fallback).

How it is wired
  • slurm.conf → AuthAltTypes=auth/jwt, AuthAltParameters=jwt_key=/var/spool/slurm/jwt_hs256.key
  • slurmrestd started with -a rest_auth/jwt — JWT only. The UNIX-socket local auth plugin is not loaded, so every call must carry X-SLURM-USER-NAME + X-SLURM-USER-TOKEN
  • Token resolution in SlurmClient.from_cluster() is SlurmCluster.jwt_token (DB field) → /etc/slurm/slurm_jwt.token (file) → SLURM_JWT (env) — first non-empty wins
  • Token file: ${BASE_ETC}/slurm/slurm_jwt.token on the host. The bind to /etc/slurm/slurm_jwt.token is declared only in docker-compose-dev.yml and docker-compose-prod.yml; the BASE docker-compose.yml gives coldfront only ${BASE_ETC}/slurm:/srv/slurm_etc. On a host that runs the base compose alone (a bare-metal prod host with an empty SLURM_BIN, where start.sh skips the prod overlay) the file is simply ABSENT inside the container — that is expected, and the token must come from SlurmCluster.jwt_token instead
  • Renewed by the django-q task refresh-slurm-jwt every 6 hours (17 */6 * * * → coldfront refresh_slurm_jwt); with the 30-day lifespan (scontrol token lifespan=2592000) that tolerates ~120 consecutive failures before auth is lost. start.sh init additionally installs a host crontab at 03:00 as a backstop (dev: docker exec <cluster>-slurmctld; prod: scontrol on the host PATH). Changing the schedule requires restarting qcluster, not just coldfront
  • ./start.sh slurm start and slurm restart regenerate the token on the way up (5 retries × 2 s backoff)

Why a lapsed token is serious — and when the CLI fallback applies

JWT tokens expire (30 days). The 6-hourly refresh-slurm-jwt task renews them long before that, but if it keeps failing the token lapses — and on a bare-metal cluster such as cluster-x there is no automatic CLI rescue: with the default settings.REQUIRE_SLURM_CLI=False a REST failure logs an error and skips the mutation. The sacctmgr fallback is only taken when the cluster is Docker (is_docker=True), when REQUIRE_SLURM_CLI=True, or in --dry-run; account and user-assoc deletes plus parented account creates are CLI-by-design and always show up as cli rows. Watch Slurm Sync Metrics — a sudden spike in cli rows is the signal to regenerate the token.

A node appearing as down* or idle* in sinfo (asterisk suffix) means slurmctld is not receiving a heartbeat from slurmd. This is independent from the container state — docker ps can still show the node container as Up while Slurm considers it unreachable, because the slurmd process can hang while its TCP socket (port 6818) remains open.

Which host are you on? Container names are always <cluster>-<service>. In dev the cluster is my_cluster-dev (my_cluster-dev-slurmctld, my_cluster-dev-cn-01, my_cluster-dev-login01). On production cluster-x (mgmt-host) only the control plane is containerized (cluster-x-slurmctld, cluster-x-slurmdbd, cluster-x-slurmrestd) — the compute and login nodes are bare metal, so there is no node container to inspect or restart. Substitute the cluster prefix in every command below, and on bare-metal nodes use ssh <node> journalctl -u slurmd / ssh <node> systemctl restart slurmd in place of the docker calls.
Symptoms

  • scontrol show node <name> reports State=... NOT_RESPONDING with Reason=Not responding [root@...].
  • docker ps shows the node container as Up.

Why this happens

On container recreate, slurmctld marks disconnected nodes as DOWN. The slurmd entrypoint attempts a background scontrol update state=resume on startup — if that hook is missing from the image or was skipped, the node stays down* until manually resumed. Bare-metal nodes (production cluster-x) have no such hook — the Ansible slurmd.service unit never self-resumes, so a node left DOWN after maintenance always needs an explicit scontrol update NodeName=<name> State=RESUME Reason="" from the controller. Separately, a long-lived slurmd can hang (rare) without exiting; the listening socket persists, so the only reliable signal is a stale log file timestamp.

Researchers can register a real IO Number now and put it on hold until funding is confirmed. The switch lives on the IO Number itself (My Usage & Billing → Cost Centers → / Edit), not on the project: one IO often funds several projects and allocations, and it is the unit the PI recognises on the invoice. Staff can pause, resume or edit any IO Number from Billing Management → IO Numbers (/billing/cost-centers/all/).

What "paused" means
  • Never charged. Every allocation whose Pay IOs are all paused is recomputed is_billable=False / no_charge. The rule engine (billing_rules.recalculate_allocation_billing) honours the flag, so a "Computing Billing" pass can never re-arm it — unlike a hand-set is_billable, which the recalculation overwrites.
  • Cannot fund new work. Hidden from every project / allocation picker and refused server-side as a new link (link view, allocation assign, allocation create, project create/update, Django Admin via AllocationCostCenter.clean()).
  • Existing links are KEPT. Nothing is unlinked — an allocation with no Pay IO would fall into io_hold and the sync would freeze its account. Storage, quotas, directories and project links are untouched.
  • Job submission is blocked on the paid Slurm account: GrpSubmitJobs=0, re-asserted on every sync pass. The free default/scavenger account is a sibling leaf under pi-<user> and is never touched, so nobody is locked out of the cluster.
  • Audit. paused_at / paused_by on the row; resuming is a deliberate action (quick toggle or Edit Cost Center).
Guards (the pause is refused when…)
  1. the IO is a no-charge sentinel (5555555555 / 9999999999) — shared by every hardware-credit project;
  2. it funds a condo / credit_holder allocation — not pay-per-use;
  3. it co-funds an allocation with another live Pay IO — pausing one funder would leave it charged its share_percent. The PI pauses the other IO(s) too, or staff splits the allocation. The assign card likewise refuses a paused + live mix.

Reasons come from billing_rules.pause_blockers() and are shown on the button tooltip, the Edit form and as flash messages.

When it takes effect

Billing is recomputed immediately when the switch is saved. The Slurm side (GrpSubmitJobs=0 on the paid account) is written by the per-PI sync that the save dispatches and is re-asserted by the 15-minute full sync — so a job submitted in the first moments after a pause may still be accepted, and after a resume submission can take up to one sync pass to come back.

Ownership rule for GrpSubmitJobs

ColdFront owns the zero on allocation accounts: paused ⇒ write 0; resumed ⇒ write -1 only when the live value is 0. An operator-set positive GrpSubmitJobs is left alone. To freeze a non-paused allocation account by hand use MaxJobs/GrpJobs=0 (respected by the sync), never GrpSubmitJobs=0 — it would be lifted on the next pass.

Report-time semantics (know this before promising dates)

is_billable is applied when reports are generated (billing_queries._apply_billing_filters). Pausing mid-period removes the whole period's usage of that allocation from billable reports and invoices; resuming brings it all back. paused_at is recorded but not consulted — it is the hook if time-boxed billing is ever wanted.

Helpdesk ticket

Pausing opens one helpdesk ticket through the ticket bridge with the PI as submitter — title Billing paused on IO Number: <PI> - <IO>, body listing the paid allocations affected (Slurm account, share) and the admin link. It is recorded as a HelpdeskTicketLink with event io_pause; resuming posts the resolving follow-up ("Billing on IO Number X was resumed by <user>"). A later pause opens a new ticket. Bridge off / API down → the legacy queue e-mail, like every other bridge event. Saving the label or Active flag never opens a ticket — only the pause flag flipping does.

Related settings
  • Active ("Available for new projects and allocations") is a separate lifecycle flag: unchecked hides the IO from pickers and refuses new links, but existing links keep billing — the state for an expired grant whose past usage must still be invoiced.
  • Cluster reset period is monthly (cluster-x PriorityUsageResetPeriod=MONTHLY, 2026-09-21); Core Hours Reset should be set to Monthly. The default (scavenger) seed is 180,000 core-h/month (6,000 units × 30 days) — SlurmCluster.default_core_hours.

CLOACK clusters expose Slurm partitions by purpose and QoS by use case. Pick the partition that matches your workload, and the QoS that matches the priority you need. The names below are the ones live on the production cluster cluster-x.

Partition naming convention
  • CPU partitions by billing tier: low, med, high — differ in TRES billing weight (cost per core-hour).
  • GPU partitions by hardware: a100, l40s, h100, h200 (OrgA) and b200, b300 (OrgB) — submit to the partition matching the GPU type your job needs. A job on a GPU partition must request GPUs (--gres=gpu:N or --gpus=N) or it is rejected at submit.
  • Free partition: scavenger — preemptible and never billed.
QoS

Your QoS is decided by the account you submit under — it marks the account class, it is not a priority dial you turn. Your allocation already carries the right default, so most jobs never need --qos at all.

  • scavenger — free, preemptible. Long max wall, no cost. Your job may be killed if a paid job needs the resources. Free work is still metered against your allocation's core-hour budget — 180,000 core-hours on a default cluster-x allocation — and that budget resets monthly.
  • condo — hardware-credit (condo) accounts, and class — course accounts. These, and the elevated GPU tiers orga2/orga4, are pinned to your allocation by staff — you never pass them by hand.
  • orga — standard paid QoS for batch work on OrgA accounts (OrgB accounts use orgb), where your allocation enables it.
Example submissions
sbatch --partition=med --qos=orga job.sh            # paid CPU work
sbatch --partition=scavenger --qos=scavenger run.sh  # free, preemptible
srun  --partition=a100 --qos=orga --gres=gpu:1 --pty bash  # interactive shell on an A100 (GPU request required)

Partitions and QoS are held per SlurmCluster and managed in Django Admin. The same naming convention is used for all clusters so users can submit jobs the same way regardless of cluster. Where the rows come from depends on SlurmCluster.manage_config: a ColdFront-managed dev cluster is seeded from ColdFront, while an externally-managed cluster such as production cluster-x has its nodes and partitions mirrored from the live controller by import_slurm_cluster. QoS is the exception — ColdFront owns QoS policy, so the reverse-import skips it unless --with-qos is passed.

Convention
  • CPU partitions: low / med / high — one per billing tier. SlurmPartition.kind = cpu. SlurmPartition.tier_code (low/med/high) is the join key: rate lookup matches BillingRate.tier_code against the partition's own tier_code field, never against its name.
  • GPU partitions: named after the hardware (a100, l40s, h100, h200 on the OrgA side, b200, b300 on the OrgB side). Set kind=gpu and hardware=<model> on the partition. The hardware field is the stable identifier used by billing and reporting. Organization access is enforced by AllowAccounts on the partition — never by QoS.
  • QoS marks the account class (role taxonomy, since 2026-09-08): SlurmQOS.role (default / paid / condo / class) plus an optional affiliation FK. Production (cluster-x) runs scavenger (role default), orga (role paid, OrgA), orgb (role paid, ORGB), condo and class; the elevated GPU tiers orga2/orga4 are granted per account by pinning the QoS/DefaultQoS allocation attributes. normal and premium are retired on production — together with interactive they survive only in the dev (my_cluster-dev) seed. GPU caps live on the QoS row itself (max_tres_per_account / max_tres_per_user): non-blank means ColdFront owns the value and drift-converges it every sync pass; blank means operator-managed via sacctmgr.
  • Retiring a partition: uncheck SlurmPartition.is_available — never delete the row. The scheduled sync_bare_metal_topology re-imports whatever the live controller reports, so a deleted row comes straight back; an unchecked one disappears from the Submit Job dropdown, Cluster Detail and the resource catalog.
Seeding (idempotent)
./start.sh populate dev --partitions a100,l40s,h100,h200,low,med,high,scavenger

--partitions takes a comma-separated list of partition names, or the standard preset (low,med,high,a100,scavenger). The command targets the dev (my_cluster-dev) Docker cluster. QoS records come from the SlurmQOS model, and ensure_in_slurm=True is the only trigger for slurm_sync to create (or assign) a QoS — there is no hardcoded fallback. Externally-managed clusters such as cluster-x import their QoS with the flag off and keep their own sacctmgr policy.

BillingRate ↔ Partition join

Use BillingRate.tier_code to link a rate to a CPU partition without relying on partition_name strings. Set tier_code = low | med | high on each rate row; the billing engine reads this field for cost lookups. GPU partitions do not use tier_code — they are joined by SlurmPartition.hardware.

Multi-cluster

Each SlurmCluster gets its own copy of the partition/QoS set. For a dev Docker cluster, run the populate command after creating it, or add the rows in the admin. For a bare-metal cluster such as cluster-x, do not run populate — it seeds fake billing rates and job records: register the cluster with import_slurm_cluster --cluster <name> and let the scheduled sync_bare_metal_topology keep partitions and nodes in step with the live controller (QoS is skipped unless you pass --with-qos). slurm_sync bootstraps the flagged QoS in slurmdbd, and cluster_manager writes slurm.conf — but only while SlurmCluster.manage_config is on. On an externally-managed cluster such as cluster-x (manage_config=False) the per-cluster mirror {BASE_DATA}/slurm/{cluster}/slurm.conf is the absolute source of truth: ColdFront never generates it. Partition/node edits go into the mirror, then scontrol reconfigure, then import_slurm_cluster --update to re-sync the DB.

End-to-end billing pipeline. Each link in the chain is editable from Django Admin.

1. BillingRate — rate catalog

/admin/cloack_sync/billingrate/

  • cluster / partition_name — scope (blank = all clusters / all partitions)
  • rate_type — cpu_full, cpu_om, gpu_full, gpu_om, plus the two storage rows: storage = cache (the flash/SSD share) and backup = object (the object/bulk share). Those are the catalog words — the Rate Types table describes the two storage rows as cache and object.
  • rate_per_unit — $ per SU (1 SU = 1 hour of the resource: CPU core-hour, GPU-hour), or $ per TB-month for storage / backup
  • effective_from / effective_to — date-versioned. Leave effective_to blank for active rate.

Two-track pricing: *_full for pay-per-use PIs (compute + O&M bundled). *_om for hardware-credit holders (lower — O&M only).

2. AllocationBilling — per-allocation config (one per Allocation)

/admin/cloack_sync/allocationbilling/ — computed by billing_rules.recalculate_allocation_billing. This is an explicit action, not a signal: the Compute Billing button on /billing/report/, the Django Admin action, or coldfront recalculate_billing --all (the command requires exactly one of --all / --allocation / --project / --pi; a bare invocation errors out).

  • io_number — OrgA service-center cost code. No IO → is_billable=False automatically.
  • department — a mirror of Project.department, which is the single source of truth for Slurm tree placement. The hierarchy is root → school → dept → pi-<user> (structural) → {default, project} leaves → users, and the per-PI department is resolved from the PI's projects in collect_coldfront_acc_info. This field is a legacy fallback that only fills in for PIs missing from that map.
  • billing_type — pay_per_use / credit_holder / no_charge
  • is_billable — single source of truth for whether the allocation is charged. False = tracked but $0.
  • storage_tb / backup_tb — provisioned TB, mirrored from the Project. storage_tb is the Cache (TB), billed at the storage (cache) rate; backup_tb is the Project Storage (TB) total — which includes the cache — billed at the backup (object) rate. Both are $ per TB-month.

Sets is_billable=False + billing_type=no_charge for: default allocations, OrgB PIs (orgb-*), allocations without an IO Number, allocations carrying a no-charge sentinel IO, and allocations whose pay IOs are all paused by the PI (CostCenter.billing_paused).

PI billing hold — CostCenter.billing_paused (shipped 2026-09-21). The PI pauses an IO from My Usage & Billing → Cost Centers; staff can pause, resume or edit ANY PI's IO from Billing Management → IO Numbers (/billing/cost-centers/all/) or the Django Admin change form — all paths run the same guards and stamp paused_at / paused_by.

The rule engine applies the hold last, after the condo override, so a Compute Billing pass can never re-arm a paused IO. In Slurm, slurm_sync writes GrpSubmitJobs=0 on the paid account association (not per user), so nothing can be submitted there until the IO is resumed; ColdFront owns that zero and lifts it back to -1 only when the live value is 0. The free default/scavenger account is a sibling leaf under pi-<user> and is never touched, and existing IO links are KEPT (unlinking would drop the allocation into io_hold).

Cannot be paused (billing_rules.pause_blockers): a sentinel IO, an IO funding a condo / credit_holder allocation, or an IO that co-funds an allocation with another LIVE pay IO. Pausing opens a helpdesk ticket; resuming resolves it.
No-charge sentinel IOs — 5555555555 (OrgA) and 9999999999 (OrgB) mean “this is a real paid project, provisioned like any other, but nobody is charged”. Saying it with an IO rather than by leaving the field empty is what keeps the allocation protected by every IO gate (the io_hold freeze, the ≥1-pay-IO rule, the last-pay-IO guard) — and unlike un-ticking is_billable by hand, it survives the next Compute Billing. Selecting one is staff-only, on the Create Project IO select, the Allocation Request pay-IO picker and the per-allocation IO Assignment card.

Consequence: every non-default allocation now needs a pay IO, OrgB included. A OrgB request attaches its sentinel automatically; an OrgA paid allocation with no IO still gets the synthetic 10000+ placeholder, flagged [PLACEHOLDER] by scripts/project_approvals.sh --ios, because it genuinely owes money and must not be silently zeroed.

Condo is separate. It is the staff-only “Hardware Credit Holder (condo)” checkbox on Create Project, no longer inferred from the IO number, and it overrides the rows above: billing_type=credit_holder with is_billable=True, which is what HardwareCreditPool accounting needs.
3. HardwareCreditPool — prepaid credits from hardware purchase

/admin/cloack_sync/hardwarecreditpool/

  • allocation — FK to the Allocation receiving the credits
  • hardware_value — dollar value of the hardware
  • total_credits — compute hours granted (e.g. 87600 GPU-hours)
  • credit_type — cpu, gpu, storage, memory (matches BillingRate.rate_type prefix)
  • granted_date / expiry_date — validity window

Credits cover compute only. O&M is always billed in cash via *_om rates.

4. SlurmPartition.tres_billing_weights — per-partition multiplier

/admin/cloack_sync/slurmpartition/

Injected as TRESBillingWeights= in slurm.conf. Weights follow this stack's milli-dollar convention: weight = $ per unit-hour × 1000 (1 billing unit = $0.001). So CPU=55.5,Mem=5.328G,GRES/gpu=555 means $0.0555 per core-hour, $0.005328 per GiB-hour and $0.555 per GPU-hour. cluster-x runs PriorityFlags=MAX_TRES, so a job's billing is the max, never the sum: billing = max(cpus × W_cpu, mem_gib × W_mem, gpus × W_gpu) and $ = floor(billing) × 0.001 × hours. Every estimate surface (Submit Job modal, cli_filter.lua, job_submit.lua) uses that formula when the partition has weights; the BillingRate $/SU catalog prices the job only when tres_billing_weights is blank. Hardware contributor in a shared pool — PI bought GPU/storage that other groups now use. IO of the consumer using the resource. IO of the PI who owns the hardware (receives a rebate proportional to usage).
Departmental cost-share — department covers part of the bill. IO of the department that pays. IO of the PI's grant (receives the credit / surplus).
Inter-PI collaboration — Lab A pays the bill, but the credit/report goes back to Lab B's grant. IO of Lab A. IO of Lab B.
Agency overhead / rebate return — specific IO designated to collect rebates automatically. — Destination IO for the rebates.
When to leave Receive blank
  • Standard paid allocation with no hardware pool, no cost-share, no financial collaboration → only Pay (outgoing) is needed.
  • Most OrgA PIs do not need to fill in Receive.
  • Default / scavenger allocations are never billed → they need no IO at all, so both Pay and Receive stay blank.
  • OrgB allocations are never charged, but they are still paid-shaped and still need a Pay IO: the no-charge sentinel 9999999999 (OrgA sentinel: 5555555555) is attached automatically, which is what keeps every IO gate (io_hold freeze, ≥1-pay-link, last-pay-link guard) protecting the allocation. Receive stays optional.
Notes
  • An IO with direction Pay only cannot be selected in the Receive list, and vice versa (set Both on the Cost Center if you need either role).
  • Receive is currently a declaration of intent — it's recorded on the allocation and visible in billing reports / Admin, but the credit-distribution pipeline is not yet automated. Mark it correctly today so future automated rebate runs route to the right IO.
  • An IO cannot be narrowed from Both to Pay only while allocations use it as Receive, nor to Receive only while allocations use it as Pay — the system blocks the change in either direction.
  • Pause billing is a separate control from the direction. While an IO is paused it is never charged, every allocation funded only by paused IOs is recomputed is_billable=False / no_charge, it is refused as a NEW Pay/Receive link, and job submission is blocked on every paid allocation it funds (GrpSubmitJobs=0 on the account association). Existing links, Project Storage and the free scavenger allocation are untouched. Sentinel IOs, IOs funding a condo / credit_holder allocation, and IOs co-funding an allocation with another LIVE pay IO cannot be paused. Pausing opens a helpdesk ticket; resuming resolves it.
  • Un-ticking Active is not a way to stop charges: an inactive IO is hidden from the pickers and refused as a new link, but existing links KEEP BILLING. Use Pause billing for that.

PIs register, edit and pause their own IO Numbers on Cost Centers (/billing/cost-centers/, sidebar entry next to My Usage & Billing), and link an existing IO to a project or to a specific allocation from the Project Detail page. Staff pause, resume or edit any PI's IO from Billing Management → IO Numbers (/billing/cost-centers/all/), or via Django Admin → /admin/cloack_sync/costcenter/ — all three paths run the same guards and stamp paused_by / paused_at.

  • Collaboration — workload calendar at /extensions/calendar/, ticket collaborators (add_collaborator / remove_collaborator), shared queue visibility for cross-team work, and a dashboard Collaboration section listing tickets where you are an approved collaborator (reviewer, shadow, mentor, …) but not the owner.

Staff Help (In-App Reference)

The following sections are available to every helpdesk staff user at /extensions/staff-help/. They summarise the Standard Operating Procedures (SOPs) enforced by the helpdesk automation.

1. First Quality Response (FQR)

FQR is the quality standard for every first interaction. A good FQR is prompt, complete, and effective — addressing the user’s concern meaningfully and moving toward resolution on first contact.

Pre-Work Checklist (before responding):

  • Research the issue — review error codes, logs, documentation
  • Know the user — check RT history, environment, previous cases, severity/SLA
  • Know the offerings — scientific software vs system, support boundaries, mission-critical
  • Identify resources — workflows, KB articles, SMEs, swarming guidance

Core Elements of an FQR:

  • Clearly Defined Scope — ask clarifying questions
  • Progress Toward Resolution — move it forward on first contact
  • Empathy & Human Communication — no robotic phrasing
  • Alignment on Urgency — match the user’s sense of priority
  • Minimal User Effort — reduce back-and-forth
  • Timely Response — meet SLA while preparing
  • Leadership and Guidance — communicate the resolution plan

4. 3-Strike Follow-Up Process

When a user doesn’t reply to a staff message, the system sends automatic follow-up emails at fixed business-day intervals. A user reply at any point resets the strike counter.

  1. Strike 1 (after 2 business days) — gentle reminder
  2. Strike 2 (3 business days after Strike 1) — checking in, encouraging engagement
  3. Strike 3 (3 business days after Strike 2) — case archiving notice; ticket closes
5. Public Feedback Categories

Categories flagged show_on_submit=True in Django Admin (Helpdesk Extensions → Ticket categories) appear as an opt-in Feature feedback? dropdown on the public submit form. When a user picks one, the ticket is auto-assigned to the category’s default_assignee, bypassing the tier / AssignmentPolicy chain entirely.

Seeded by migration 0028_ticket_category_feedback under the “Product Feedback” domain:

  • ColdFront Feature Feedback → admin1
  • Helpdesk Feature Feedback → admin1

Product owners can be changed per-category in Django Admin; new feedback channels can be added by creating another category with show_on_submit checked and an assignee set — no code change required.

6. Response Templates

Default templates are seeded and available from the ticket composer. Picking a value in Send email as auto-substitutes these placeholders in the Comment box — staff can still edit before submitting, and a server-side safety net scrubs any leftover tokens on save: {name} (submitter), {your_name} (assigned staff), {ticket_number}, {issue} (ticket title), {signature} (Staff Members → Signature field in Django admin, falls back to the user’s full name), {survey_url} (per-ticket satisfaction-survey link).
