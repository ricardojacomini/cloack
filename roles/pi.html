PI — managing a project, its allocations, and billing

Who you are + scope

You are a Principal Investigator with a Portal account that has the PI flag on your UserProfile. You own one or more Projects, request Allocations against them (default scavenger / paid Pay-Per-Use / condo Hardware-Credit), set spend caps, add users to your projects, request project storage and class resources, and read the billing report monthly. Authentication-wise you are a normal user: read user.md for the login flow and the job-submission basics.

If you also operate the cluster (deploy services, configure Slurm) you are a different role: read admin.md. If you handle helpdesk tickets you are also Staff: see staff.md.

Quick start

1. Accept the Terms of Service

Before you can do anything as a PI you must accept the current ToS. You will see a banner at the top of every portal page until you do. Click the banner, check the box, submit. ToS acceptance is also required for every user you add to your projects: a member's Slurm association and login shell are created only after they accept.

You can re-read what you agreed to at any time: on /user/user-profile/ the Terms of Service row shows Accepted vX as a link that opens the exact version you accepted (read-only, with a Print button).

2. Create a project and request an allocation

/project/create/                       → create a new project
/project/<id>/                         → project detail page
  Click "Request Resource Allocation"  → choose a resource (Cluster)

A project with empty / default abbreviation is the scavenger-only default project: it cannot host paid allocations, and the request button is replaced by a note. To request a paid allocation, give the project a real abbreviation (proj1, alpha, ...) when you create it. The project description must have at least 150 words.

For paid allocations:

  • IO Number: your funding source. Every non-default allocation needs a pay IO, OrgB included. A project that must not be charged carries a staff-set no-charge IO (5555555555 OrgA / 9999999999 OrgB) and reports $0 while staying fully provisioned.
  • Project Storage is requested AFTER creation, from the "Project Storage" card on the project page (Project Storage TB = total capacity, includes the Cache; staff approve in Storage Review).
  • Spend cap: a new paid allocation starts with its cap not set, and job submission on that Slurm account is held until you set Weekly Cap ($) / Weekly Cap (SU) or click No cap (see §4). Free allocations start with no cap.

Submitting the request opens a helpdesk ticket in your name: you get the acknowledgement e-mail with the ticket link, can add information by replying, and the ticket resolves itself when staff approve or deny the allocation. The same happens when you create a project or ask to become a PI.

You may request a second allocation on the same project. Until staff assign a SubProject suffix during review, both allocations resolve to the same Slurm account name and approval is refused, so say in the justification what the second allocation is for.

To retire an allocation you no longer need, open it and click Request Deletion (a reason is required). Only a ColdFront administrator can delete an allocation; your request opens a helpdesk ticket in your name and the allocation shows "Deletion requested" until it is handled. A request that is still New can simply be withdrawn with Remove Pending Request.

3. Add users to a project

/project/<id>/ → "Add Users"

Users must already have a Portal account (campus ID users get one at first login; others register via /user/orga/register/ or /user/orgb/register/) and they must have accepted the current ToS. Add them to the allocation, not only the project: membership of an allocation is what creates the Slurm association and grants the cluster login shell. Provisioning is immediate once the ToS gate is clear.

4. Set or update the spend cap

/allocation/<id>/ → "Set Cap" (or "Update Cap") → amount in $ or SU → save
                   → or click "No cap"
  • Values: 0 = not set (job submission held on that account), −1 = no cap, N = the cap. The field is seeded 0 on paid allocations and −1 on free ones.
  • Unit: $ or SU (1 SU = $0.001). Weekly Cap (SU) is SU, not core-hours: a core-hour costs the partition's billing weight in SU, so 1,000 SU is $1.00 whatever the partition. If both fields are set the dollar cap wins.
  • Period: the field is named Weekly, but the window is the cluster's usage reset period, when Slurm clears the counter the cap is checked against. The cap card says which one applies ("per month", "per week"), and the gauge, sbalance --week and the Submit Job messages follow the same window.
  • Conversion: $X × 1,000 × 60 = GrpTRESMins=billing on the account association, across all partitions at once.
  • One cap per allocation; users sharing the allocation share the cap. At the cap, jobs queue with reason AssocGrpBillingMinutes until the period resets; a job whose projected usage would cross the cap waits instead of being killed.
  • The Budget (SU) card shows the remaining SU, how many hours it buys on each partition, and the SU reserved by running jobs.

5. Read the billing report

/billing/report-by-pi/                  → your projects, per allocation
/user/user-profile/ → "My Usage & Billing"  → charges + invoice PDF
/storage/                               → My Storage (provisioned + pending)
  • Compute is billed in SU: the SU Slurm counted for the period, times $0.001. The CPU (est.) and GPU (est.) columns price the hours at the catalogue rate for comparison and are never summed. Periods recorded without SU (older data) fall back to the legacy rule: a period that used GPU is charged on GPU hours only, with CPU hours shown for transparency.
  • Cache and Project Storage are billed monthly regardless of compute activity; the "Project Storage" card shows the monthly estimate at current rates (cache × Cache rate + total × Project Storage rate) for the provisioned and any pending values.
  • Rows appear only after staff run Computing Billing on the Billing Report; the page never gains rows on its own.
  • Invoice status per period: Pending, then Paid, Overdue or No Charge. An Overdue invoice pauses every pay IO of the allocation automatically once the grace window passes (by default from the 1st of the third month after the invoiced month). Allocation Detail shows an amber "will be paused from " banner before, red afterwards; the pause lifts when the period is marked Paid or No Charge.

6. Class resources

Projects → My Classes (/classes/) → "Class Request" (/classes/request/)

Fill in the course code, name, dates, school and department, and the roster (Full Name,campus ID,external email; OrgA addresses are refused, the link must reach a mailbox the student already owns). On approval staff create a class project <pi>_<code> with an allocation that ends with the course, one <code>-ext-<campus-id> account per student, and e-mail each student a password link at the roster address. From the class page you can add TA managers, resend password links to selected students, and Request more students (one open request per class). When the course ends the class is marked Ended and a teardown ticket is opened; nothing is deleted automatically, and Delete Class removes only the <code>-ext-* accounts.

Primary department

You choose a primary department when you ask to become a PI (User Profile → Upgrade Account). The list only offers departments of your own affiliation, and Advanced Research Computing is reserved to cluster administrators. When staff approve the request, your default project is created in that department, which is also where your account sits on the cluster.

To change it later, use the Primary Department row on /user/user-profile/. Your default project moves with it, and the cluster account follows within a few minutes. Paid projects keep the department you set on each project. If you have no primary department yet, or you hold the reserved one without being a cluster administrator, a banner on every page asks you to choose one. Nothing is blocked in the meantime.

Billing model decision table

If... ...pick
Default scavenger PI project (no abbreviation, no IO) No Charge, set by the billing rule engine when staff run Computing Billing
OrgB PI (orgb-*) No Charge: funded by the OrgB programme; the allocation carries the 9999999999 no-charge IO
Paid project that must not be charged (internal / CLOACK) No Charge: staff attach the 5555555555 no-charge IO; provisioned like any paid project
Paid project, IO number, no upfront hardware purchase Pay-Per-Use
Paid project, IO number, you bought hardware credit Condo (Hardware-Credit holder; staff tick the condo box at creation)

Cost Center setup (multi-IO)

You can pool several IO Numbers under a single project / allocation:

/billing/cost-centers/                  → manage your Cost Centers (IO Numbers)
  → "Add Cost Center"
  → Link a Cost Center to a project       → project-level link
  → Assign a Cost Center to an allocation → allocation-level link (role: pay)

The allocation-level pay link is what counts. A paid allocation without one is frozen on the Slurm side: its account is neither created nor touched, and the allocation page shows the hold. A paid allocation can never be saved without a pay IO; paused or inactive IO Numbers are refused as new links (existing links are kept). Changing the IO Number on Update Project puts the project under Billing Changes Pending Review and opens a ticket for staff to validate it.

Pause billing on an IO Number

Register your real IO now and put it on hold until funding is confirmed:

/billing/cost-centers/  → ⏸ on the IO's row   (or Edit Cost Center → "Pause billing and job submission")

While paused, the IO is never charged, cannot fund new projects or allocations, and job submission is blocked on the paid allocations it funds. Existing links, Project Storage and your free scavenger allocation are untouched: you keep computing for free. A helpdesk ticket is opened so staff know; resuming (▶) is a deliberate action that resolves it.

The pause is refused when the IO co-funds an allocation with another live IO (pause those too, or ask staff to split the allocation) or funds a Hardware-Credit (condo) allocation. Active is different: unchecking it hides the IO from new pickers but existing links keep billing; use Pause to stop charges.

Spend cap: dollars vs SU

Cap Stored as When to use
Weekly Cap ($) $X × 1,000 × 60 billing-minutes Most allocations. A predictable spend bound per usage period.
Weekly Cap (SU) SU × 60 billing-minutes When you think in Slurm's own units. 1,000 SU = $1.00.

What one SU buys differs per partition because of TRESBillingWeights: the rate card on /billing/rates/ and the Budget (SU) card translate the remaining SU into hours per partition.

QoS pins

QoS and DefaultQoS on Allocation Detail are read-only for PIs. Staff use them to pin an account to a QoS class (condo, class, an elevated GPU tier); blank means the cluster default for your account class.

Troubleshooting

Symptom Likely cause Fix
Banner says "Accept Terms of Service" but I already accepted Old ToS version superseded by a new one Visit /user/user-profile/ and accept again; everything you provisioned before stays valid
Adding a user to a project does nothing visible in Slurm They have not accepted the ToS yet, or they were added to the project but not to the allocation Email the user the ToS link and add them to the allocation; provisioning fires immediately once both hold
"Request Resource Allocation" button is not shown This project is a default project (no abbreviation) Create a new project with a real abbreviation; default projects are scavenger-only by design
My second allocation on a project stays New Both allocations resolve to the same Slurm account name until staff set a SubProject suffix Reply on the ticket; staff set the suffix and approve
Allocation is Active but jobs are rejected with Invalid account The Slurm account is not provisioned yet, or the user's ToS gate has not cleared Wait for the next sync (every 15 minutes) or ask staff to run it
Jobs on a paid account are held (AssocGrpSubmitJobs) The spend cap is not set yet, or every pay IO of the allocation is paused Set a cap or click No cap on Allocation Detail; resume the IO on My Cost Centers
Cache charge shows $0.00 for a small share TB × rate per TB-month rounds below one cent Expected at small sizes; the ratio is correct
Billing report shows nothing for the past month Computing Billing was not run yet By design: billing periods are written only when staff press the button
Hardware Credit pool reports 0 hours despite usage The allocation's billing type is not Hardware Credit Holder Ask staff to correct the AllocationBilling row
Red "Invoice overdue" banner on my allocations A billing period of the allocation is Overdue past the grace window, so its pay IOs were paused Settle the invoice; when staff mark the period Paid the pause lifts automatically
