QoS and GPU limits: for helpdesk staff and ColdFront admins

Who you are + scope

You answer "why is my GPU job pending when the cluster has free GPUs", grant a lab more GPUs, or change a tier limit. You are a ColdFront staff member or superuser: QoS pins are edited on Allocation Detail, tier limits in Django Admin. The user's view of QoS is in user.md (QoS section); the PI's view of a pin is in pi.md ("QoS pins"). SU budgets (how much a lab may spend, not how many GPUs it may hold at once) are in su-budgets.md.

Two different kinds of limit apply to a GPU job, and they answer different questions:

  • Budget (GrpTRESMins, in SU): how much the account may consume in the usage period. See su-budgets.md.
  • Concurrency (MaxTRESPerAccount, MaxTRESPerUser, GrpTRES): how many GPUs may be in use at the same time. This guide.

The values in the examples (orga at 16 GPUs, orga2 at 32) are examples; the real ones are on Admin > Slurm QOS Definitions and in sqos all.

Quick start

1. Read what applies to an account or a job

sqos all                                   # every QOS and its limits
sqos account=<acct>                        # QOS list, DefaultQOS and GrpTRES of one account
sassoc <user>                              # account x partition x QoS combinations
squeue -j <jobid> -O jobid,account,qos,partition,reason,tres-alloc:60

2. Find out why a GPU job is pending

squeue reason Limit that holds it Where it lives
QOSMaxGRESPerUser MaxTRESPerUser of the job's QOS QOS row (Admin > Slurm QOS Definitions)
QOSMaxGRESPerAccount MaxTRESPerAccount of the job's QOS QOS row
AssocGrpGRES GrpTRES on the account or any ancestor (condo purchase size; the PI GPU cap on pi-<user>) account association (sqos account=<acct>)
AssocGrpBillingMinutes SU budget, not a GPU limit su-budgets.md
Resources / Priority No limit: the GPUs are busy or other jobs are ahead nothing to change

Slurm never starts part of a job: a 12-GPU job with 8 GPUs of room left waits whole. A job held by a limit does not reserve GPUs, so a smaller job that fits can start ahead of it.

3. Give one allocation an elevated GPU tier

On Allocation Detail, set QoS and DefaultQoS to the tier (orga2, orga4). The selects list the cluster's QOS names; saving dispatches a sync for that PI. Revoke by setting both back to "cluster default". The pin moves every member of that account off the standard tier, so limits of two tiers never stack on one account.

4. Change a tier limit

Admin > Slurm QOS Definitions > the row > Slurm Configuration: MaxTRESPerAccount, MaxTRESPerUser, Priority. Do not change them with sacctmgr on a row that has Ensure in slurm ticked: the sync converges them back within 15 minutes. Run coldfront sync_slurm --dry-run first; it prints would set ... on QOS X (live ...) for every difference.

5. Condo (purchased hardware)

The condo QOS carries no limits (every owner shares it). The purchase size lives on the condo account, from two condo-only allocation attributes shown on Allocation Detail:

Allocation Detail row Written to Slurm as
GrpTRES (account) GrpTRES on the account association: all members together
GrpTRES (per user) GrpTRES on every member's association in that account

Blank = never touched by the sync. Check with sqos account=<acct>.

Reference matrices

QoS classes

An account's QoS marks its class; it is not a priority knob. On a cluster where any QOS row carries a Role, the sync gives each account the rows of its class:

Account class Decided by Matching QOS rows
condo AllocationBilling.billing_type = credit_holder (checked first) pinned per allocation (QoS/DefaultQoS)
default default (free) allocation role default (e.g. scavenger)
paid any other allocation role paid whose affiliation matches the account's root (e.g. orga, orgb)
class course accounts pinned; never matched automatically

Lists are strict (no scavenger appended to a paid account). DefaultQOS is scavenger when it matched, else the first match. An account whose class matches no row is left untouched and logged as a WARNING. A cluster whose QOS rows all have a blank Role keeps the older free/paid policy.

GPU concurrency limits: where each lives and what it counts

Limit Set in Counts Adds up across accounts? Adds up across QOS?
MaxTRESPerAccount QOS row GPUs of one account, under that QOS no no
MaxTRESPerUser QOS row GPUs of one user, under that QOS yes (every account of the user) no
GrpTRES (account), condo Allocation Detail (condo) GPUs of one account, any QOS no yes
GrpTRES (per user), condo Allocation Detail (condo) GPUs of one user in one account no yes
PI GPU cap (MaxTRESPerPI) Allocation Detail (staff row) GPUs of every account and user under the PI yes (every account of the PI) yes

A job must fit every limit that applies; the tightest one decides. Grp* limits are hierarchical: a limit on an account also caps every account below it in the tree.

Ownership rules

Field Blank Filled
QOS MaxTRESPerAccount / MaxTRESPerUser operator-managed: the sync never sets or clears it ColdFront sets it at creation and converges drift every pass
QOS Priority n/a (always a number) written as-is, 0 included, on rows with Ensure in slurm
Condo GrpTRES (account / per user) never touched converged every pass
QoS / DefaultQoS pin cluster default for the account's class overrides the class; partial fills are completed

Clearing a filled limit: blank the field in Admin and clear it in Slurm (sacctmgr modify qos <q> set MaxTRESPerAccount=gres/gpu=-1), because a blank field is no longer managed and is left as it is.

Worked example: one PI, three accounts, QOS orga (PA 16, PU 16)

Three different users submit, in this order, 12 GPUs on account A, 8 on B and 12 on C:

Limits in force A (12) B (8) C (12) GPUs in use
MaxTRESPerAccount=16 only runs runs runs 32
PI GPU cap 16 runs pending AssocGrpGRES pending 12

With the same user on all three accounts, MaxTRESPerUser=16 already holds the total at 16 (B and C pend with QOSMaxGRESPerUser), because all three accounts use the same QOS. When A ends, only one of B and C fits; which one starts first follows job priority (each account has its own fairshare), not submission order.

PI GPU cap (MaxTRESPerPI)

Goal: one GPU ceiling per PI, whatever the number of accounts, users or QOS under that PI. MaxTRESPerAccount alone cannot do it: a PI with three accounts can hold three times its value.

Mechanism: Slurm has no MaxTRESPerPI. The sync writes GrpTRES=gres/gpu=N on the PI's structural node pi-<user>. Every allocation account of the PI (default and projects) is a leaf under that node, so the hierarchical limit counts all of them together:

orga / whiting / ap /
  pi-jdoe   GrpTRES=gres/gpu=16   <- the value of the MaxTRESPerPI row goes here
    ├── jdoe          (default allocation: shows/edits the same value)
    ├── jdoe_proj1    (proj1 allocation:   shows/edits the same value)
    └── jdoe_proj2    (proj2 allocation:   shows/edits the same value)

Switch: Admin > Slurm Clusters > Slurm Account Defaults > PI GPU cap (MaxTRESPerPI), off by default. Off: pi-* nodes are never touched. On: ColdFront owns gres/gpu in the GrpTRES of every pi-* node of that cluster; a value set there by hand is cleared when no cap applies. Other TRES on the node are never written.

Value of one node, in order:

  1. The PI has a condo account under the node: no PI cap. The cap would also count the purchased GPUs; the condo account keeps its own GrpTRES (account). Such a PI keeps the per-account and per-user limits.
  2. A staff override: -1 = no PI cap, N = N.
  3. Otherwise the highest MaxTRESPerAccount GPU count among the QOS of the PI's accounts (orga gives 16; an account pinned to orga2 raises it to 32).
  4. Nothing of the above: no PI cap.

Where staff set it: the MaxTRESPerPI (PI-wide) row at the end of the Allocation Attributes table on Allocation Detail, visible to staff only and only while the switch is on. Every allocation of the PI shows the same row and writes the same value (Admin > PI GPU caps lists the overrides), so it does not matter which allocation it is edited from. Blank = the QOS value, a number = override (with an optional reason), -1 = no PI cap. The line under the box names the node, the value and where it came from; for a condo PI the box is disabled and says why. Saving writes an admin log entry and syncs that PI at once.

What stays:

  • MaxTRESPerUser on the tier QOS stays. The PI cap does not see that a user also runs under another PI; without PU, a member of two PIs could hold both caps.
  • MaxTRESPerAccount stays: redundant under the PI cap, and it is the source of the default value.

Cases with more than one pi-* node:

Case Node Value
Allocations on two clusters one pi-jdoe per cluster one value per cluster
Project under an additional affiliation pi-jdoe-orgb under the orgb root its own value; QOS without limits (e.g. orgb) give no default, so no cap

Turning it on for a cluster:

  1. With the switch still off, list who holds more GPUs today: squeue -h -t R -O account,tres-alloc:80.
  2. Still with the switch off, run coldfront sync_slurm --dry-run and read every would set GrpTRES=gres/gpu=N on pi-<user> (live M, <source>, switch off) line, then the summary PI GPU cap: X of Y pi-* node(s) would change. A dry-run computes the cap even with the switch off; a real sync does not touch any pi-* node until it is ticked. A gres/gpu=-1 line means a value left on the node by hand, which ColdFront will clear.
  3. Tick the switch. The next sync (within 15 minutes) applies it, or run coldfront sync_slurm.

Running jobs are never stopped by a new GrpTRES; it only holds new starts, with reason AssocGrpGRES. Check a node with sacctmgr show assoc where account=pi-<user> user= format=Account,GrpTRES.

Troubleshooting

Symptom Likely cause Fix
GPU job pending, cluster shows idle GPUs A concurrency limit: read the reason (table in Quick start §2) Wait, pin an elevated tier, or raise the limit
A user holds 32 GPUs although PU is 16 The user's accounts use different QOS (orga and orga2): PU never adds up across QOS Expected with tier pins; see the limits matrix
A PI holds 48 GPUs with MaxTRESPerAccount=16 Three accounts, 16 each: PA counts one account Turn on the PI GPU cap for the cluster (section above)
A tier limit edited with sacctmgr came back The row has Ensure in slurm and a filled field Edit it in Admin
sacctmgr modify account ... set MaxTRESPerUser= says Unknown option Associations have no MaxTRESPA/PU; on an account use GrpTRES Use the condo GrpTRES rows, or a QOS field
Pending InvalidQOS after a pin or a QOS retirement Queued jobs keep the QOS they were submitted with scontrol update job <id> qos=<new> (see admin.md)
