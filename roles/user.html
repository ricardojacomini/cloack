User — researcher running jobs on Portal

Who you are + scope

You are a researcher with a Portal account: an OrgA faculty / staff / student authenticating with campus ID, an external collaborator with an ext-* username, a OrgB Sciences member with an orgb-* username, or a student on a class account (<course>-ext-<campus-id>, created for one course). Your day-to-day is submitting Slurm jobs, checking quotas and bills, and managing the data in your own /home/ and /scratch/.

If you also manage allocations for a project (request a new paid allocation, set spend caps, add other users), read pi.md too. If you are a member of the helpdesk team handling tickets, see staff.md instead.

Quick start

1. First-time login

Username pattern Login URL How you authenticate
campus ID (e.g. admin1) the OrgA portal card Entra federation; MFA comes from OrgA, no separate password
ext-jsmith the OrgA portal card LDAP password (set during registration) + TOTP (Keycloak account console)
orgb-jsmith the OrgB portal card LDAP password (set during registration) + TOTP (Keycloak account console)
en540-ext-jsmith (class account) the OrgA portal card LDAP password set from the reset link e-mailed to your real address + TOTP

If you do not have an account yet:

  • campus ID users: no registration form; sign in via OrgA SSO and the account is created on first login.
  • ext-* users: open /user/orga/register/ on the portal, fill in the form (the username must start with ext-), then wait for your PI to add you to their project / allocation.
  • orgb-* users: same flow on /user/orgb/register/; the username must start with orgb-.
  • Class accounts: created by staff when your instructor's class request is approved. You receive a password link at the e-mail address on the class roster. Lost it? Use /user/accounts/password_reset/ with your real e-mail address; the portal finds the class account by it and mails only that address.

After your first successful login a banner at the top of every page prompts you to enrol TOTP in the Keycloak account console (campus ID users are exempt). Click the banner link, scan the QR code with Google Authenticator / Authy / Microsoft Authenticator, and you are done. The banner disappears within 30 minutes, when the periodic enrolment check picks up the new credential.

2. SSH to a login node

ssh <username>@<login-node-host>

Authentication on login nodes uses the same identity as the portal:

  • campus ID: browser-based Device Flow opens automatically; approve in your browser, complete MFA in Entra, the SSH session unblocks.
  • ext-* / orgb-* / class accounts / cluster admins: the terminal asks for your LDAP password and then a TOTP code (two PAM prompts via pam_kc_ssh.so).

A login shell is granted only to accounts sponsored by a PI (member of at least one allocation) who accepted the current Terms of Service. Until both hold, the account exists but SSH ends with "This account is currently not available". The shell is recomputed on every directory sync, and accepting the ToS flips it immediately.

3. Submit your first job

Three doors into the same scheduler:

  • sbatch / srun / salloc on a login node (below). On paid partitions the CLI filter prints a [BILLING] estimate and asks Proceed? [y/N]; a $0 estimate (free partition, free account, or rates not set) is admitted without the prompt.
  • Portal Submit Job (/jobs/submit/): paste a batch script, choose partition and account, see the live cost estimate before you submit. ?as_of_date=YYYY-MM-DD previews the rates of another day for budget planning; the submission itself always uses today's rates. #SBATCH lines in the script are honoured and the job runs with your login environment.
  • Open OnDemand (https://ood.<your portal domain>): Files (your home, scratch and project spaces), Shell, Job Composer, Active Jobs (with a Grafana job-stats link where enabled) and Interactive Apps.
sbatch --partition=med --account=<your-account> --time=00:30:00 \
  --wrap='hostname && date'

For longer jobs, use a script:

#!/bin/bash
#SBATCH --partition=high
#SBATCH --account=<pi>_<project>
#SBATCH --time=04:00:00
#SBATCH --cpus-per-task=8
#SBATCH --mem=32G
#SBATCH --job-name=myrun
#SBATCH --output=%x-%j.out

module load anaconda
python my_analysis.py

A job on a GPU partition must request GPUs (--gres=gpu:N or --gpus=N); without that it is rejected at submit with a message that lists the CPU partitions to use instead.

4. Check your usage and balance

squeue -u $USER          # currently queued or running jobs (or: sqme)
sacct -u $USER --starttime=now-7days   # last week's accounting
sbrief                   # count of your jobs by state
sbalance                 # SU used vs limit for every account you sit under
sbalance --week          # spend cap and usage for the current usage period
                         # (+ this week against the weekly cap, where caps are weekly)
sbalance --by-partition  # the same, split by partition

sbalance reads Slurm itself (sacctmgr, sreport, scontrol) and prints two numbers. Used is the accounting total for the period (what the invoice is based on). Available is what Slurm will still accept: the limit minus the usage Slurm counts minus the SU held by running jobs. Slurm gives older usage less weight as the period goes on, so Available can be more than the limit minus Used. sbalance --detail shows the breakdown. The portal's Allocation Detail gauge shows the same two numbers, fetched live.

Units: 1 SU = $0.001, one unit-hour of Slurm's billing TRES. A core-hour or a GPU-hour costs as many SU as the partition's billing weight says (see Cost model below), so SU is never "a core-hour".

The window is the cluster's usage reset period, the point at which Slurm clears the counter every budget and cap is checked against. The cap card on Allocation Detail and sbalance --week print which period the cluster runs (per month, per week, ...).

5. Manage data

Path Quota Backed Cost
/home/<aff>/<username> Small, per-user Yes (snapshot) Included
/home/<aff>/<username>/scratch_<pi> Symlink into the PI's scratch; same quota as /scratch No Included
/home/<aff>/<username>/projects_<pi> Symlink into the PI's project storage; same quota as /projects Per plan Billed to the PI
/scratch/<aff>/<pi> Per-PI scratch storage No Included (scratch is separate from project storage)
/projects/<pi> Per-PI project storage (provisioned capacity) Per plan Billed monthly to the PI

Project storage (the per-PI filesystem mounted at /projects/<pi>) is billed per TB-month whether or not anyone runs jobs: Cache (the flash share) and Project Storage (the total capacity, which includes the cache). Current rates: /billing/rates/. The charges show up on your PI's billing report under "Cache" / "Project Storage". When your PI has provisioned project storage, a projects_<pi> symlink appears in your home automatically (created by the directory sync, like scratch_<pi>).

Reference matrices

Slurm partitions (naming convention)

Partitions are per cluster; sinfo and sfeatures list the live set. The portal's Submit Job dropdown hides partitions staff marked unavailable. Names follow one convention everywhere:

Kind Names Notes
CPU partitions, by billing tier low, med, high Same hardware class, different TRESBillingWeights (SU per core-hour).
GPU partitions, by hardware a100, l40s, h100, h200, b200, b300 Submit to the partition matching the GPU you need. Some are reserved to one organisation's accounts (AllowAccounts). A job with no --gres/--gpus is rejected.
Free scavenger Preemptible, never billed. On some clusters scavenger is a QoS rather than a partition; sassoc shows what your accounts can use.

QoS (account class)

Your QoS is decided by the account you submit under: it marks the account class and is not a priority dial you turn. Your allocation already carries the right default, so most jobs never pass --qos.

QoS Meaning
scavenger Free, preemptible. Your job may be killed if a paid job needs the resources. Free work is still metered against your allocation's budget.
orga / orgb Paid work on an OrgA / OrgB account, where your allocation enables it. orgb accounts are funded by the OrgB programme and never billed.
interactive Priority 1000, 4-hour wall cap, for interact / srun --pty sessions.
condo, class Hardware-credit (condo) accounts and course accounts. Pinned to the allocation by staff.
orga2, orga4 Elevated GPU tiers (2x / 4x the standard per-account GPU limit). Pinned per allocation by staff; you never pass them by hand.

sqos prints the limits behind each QoS; sassoc prints the account x partition x QoS combinations you can submit to.

Cost model

Cost is partition-specific, and the numbers live on /billing/rates/ and in the Submit Job preview, not here.

  • 1 SU = $0.001.
  • Per job, Slurm bills the largest weighted resource (PriorityFlags=MAX_TRES): billing = max(cpus x W_cpu, mem_GiB x W_mem, gpus x W_gpu), with the W_* weights from the partition's TRESBillingWeights; SU = billing x hours; $ = SU x 0.001. The [BILLING] block of the CLI filter marks the winning line with <- billed (max).
  • The invoice charges the accounting total in SU, the "Used" figure of sbalance. The spend cap is checked against Slurm's own counter, which weighs older usage less (see §4). CPU-hour and GPU-hour figures priced from the rate catalogue appear beside it as estimates only.
  • Cache and Project Storage are flat per TB-month, charged every month regardless of jobs.
  • Never charged: scavenger, orgb-* accounts, default allocations, and allocations staff marked no-charge.

Sense check: on a partition whose CPU weight is 6.2 SU per core-hour, an 8-core, 24-hour job is 8 x 24 x 6.2 = 1,190 SU = $1.19. Your PI's spend cap stops a runaway long before the bill does.

Troubleshooting

Symptom Likely cause Fix
SSH ends with "This account is currently not available" or Permission denied No login shell yet: you are not on any PI's allocation, or you have not accepted the current Terms of Service Ask your PI to add you; accept the ToS on /user/user-profile/; then re-SSH and follow the prompts (password + TOTP, or the browser Device Flow)
Banner says "Activate TOTP" but I already enrolled The enrolment check runs every 30 minutes Wait, or open /user/user-profile/; if it persists open a helpdesk ticket
Job pending with reason AssocGrpBillingMinutes The account's spend cap or budget for the current usage period is used up sbalance --week to confirm; switch to scavenger (free); or ask your PI to raise the cap. The counter clears at the period boundary
Job pending with reason AssocGrpSubmitJobs (submission held) The allocation has no spend cap set yet, or the IO Number paying for it is paused Ask your PI to set a cap (or choose No cap) on Allocation Detail, or to resume the IO Number. Your free default account is never held
sbatch: error: Invalid account or account/partition combination Generic rejection: you are not a member yet, your ToS is pending, the account is not provisioned, the partition is reserved to another organisation, or the QoS is not allowed there sassoc to see your valid combinations; if the pair looks right, open a ticket so staff can read the controller log
GPU job rejected: "GPU partition requires a GPU request" No --gres=gpu:N / --gpus=N on a GPU partition Add the GPU request, or use a CPU partition
Job refused with "accept_cost not set" A non-CLI path (slurmrestd direct, a custom OnDemand app) did not inject comment=accept_cost Re-submit via sbatch / srun on the login node, or set --comment=accept_cost explicitly
Storage charge appears on the bill with 0 hours run Cache and Project Storage are charged monthly regardless of compute By design; see the storage note above
Permission denied editing /scratch/<aff>/<pi> The directory belongs to the PI, not you Ask your PI to add you to the project / allocation in ColdFront
